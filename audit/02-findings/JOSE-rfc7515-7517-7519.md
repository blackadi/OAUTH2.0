## Finding F-1 — the deployment advertises `alg: none` on two endpoints (S3)

RFC 7515 registers no `none` value in its IANA `alg` registry; unsecured JWSs are a defined concept the
specification does not endorse for production. Live metadata (probe 3):

```
userinfo_signing_alg_values_supported      = ["HS256","HS512","ES256","HS384","none"]
introspection_signing_alg_values_supported = ["HS256","HS512","ES256","HS384","none"]
```

> **⚠️ Two corrections, both established by writing to the service on 2026-08-12 (T1-13). The finding stands;
> its remedy does not.**
>
> 1. **`none` cannot be withdrawn.** **No Authlete 3.0 `Service` property lists either set of algorithms** — of
>    193 properties the only related ones are the key *selectors* `userInfoSignatureKeyId` and
>    `introspectionSignatureKeyId`. Both lists are derived from the service JWK Set, and `none` is unconditional
>    vendor output; Authlete's own `service/configuration` example in `docs/openapi-spec.json` carries it.
>    Proved by writing both selectors to `rsa-1`: **the lists changed** (`ES256` dropped out, because pinning
>    the RSA key removes the EC key as a candidate) **and `none` survived both**. Reverted; only `modifiedAt`
>    moved. `SERVICE-CONFIG-PROBE.md` §19. **This is RPL-W4's shape a second time** — a work item naming a knob
>    the vendor does not have.
> 2. **"only reachable if a client sets `introspectionSignAlg`" is wrong.** The `Client` schema has **no**
>    introspection signing property at all — 0 of its properties match `/introspect/i`. `userInfoSignAlg` does
>    exist and does accept `NONE`, so for UserInfo the advertisement is *accurate*: an unsigned response is a
>    real, selectable outcome. For introspection the member describes the default unsigned response and
>    **nothing on either side can narrow it.**
>
> So the *shape* of the finding changes: this is not a misconfiguration the deployment declines to fix, it is a
> vendor metadata document that lists `none` as an algorithm because the vendor treats "unsigned" as one.
> **JOSE-W2 becomes a documentation item** and takes MS-W3 with it. The lists also grew since this was written
> — one RSA key added six algorithms to each (probe §12).

Both advertise **`none`**. It is only reachable if a client sets `userInfoSignAlg`/`introspectionSignAlg` to
`none`, and no client does — so nothing is currently signed with `none`. But:

- FAPI 1.0 Part 2 §5.2.2 says *"shall not use `none`"* (`FAPI-1.0-PART-2-ADVANCED.md` F-2);
- for **introspection** the advertisement is worse, because RFC 9701 signed introspection exists specifically for non-repudiation, and FAPI 2.0 Message Signing requires those responses to be signed (`FAPI-2.0-MESSAGE-SIGNING.md` MS-W3);
- Module 00 teaches the `alg: none` attack (`modules/00…/README.md:114` covers `typ` values, and Module 08 Exercise 4's "forge it six ways" includes the unsecured-JWS case), so the curriculum warns against exactly what the metadata offers.

Recorded here rather than only in the FAPI entries because the root is RFC 7515: `none` is not a signature
algorithm, and a metadata document listing it as one is wrong independently of any profile.

## Finding F-2 — the two verifiers that skip RFC 7519 §4.1 checks share a root cause (S3)

Two findings already recorded elsewhere are the same defect seen twice:

| Verifier | Missing check | RFC 7519 | Recorded in |
|---|---|---|---|
| JWT-bearer assertion (`services/jwt-verification.service.ts:47`) | **`exp` not required to be present** — `mandatoryClaims: ["iss","sub","aud"]` | §4.1.4 requires a recipient to verify `exp`; RFC 7523 §3(4) requires it to be *present* | `RFC7523-…` F-1 |
| Logout token (`controllers/logout.controller.ts:76,82`) | **`iss` and `aud` never checked** — `jwt.verify` called without `issuer`/`audience` | §4.1.3: if `aud` is present and the recipient cannot identify itself in it, *"the JWT MUST be rejected"* | `OIDC-BACKCHANNEL-LOGOUT-1.0.md` F-1 |

The common root: **`jsonwebtoken`'s `verify()` validates `exp` and `nbf` by default and validates `iss`/`aud` only
when told to.** Both call sites pass `algorithms` and nothing else. So in both places the JOSE-level MUSTs are
missed in the same way, for the same reason, and the profile-level requirements (RFC 7523 §3, Back-Channel Logout
§2.6) inherit the gap.

That framing matters for remediation: fixing them as two protocol bugs invites the same omission at the next
`jwt.verify` call site. Fixing them as one JOSE-hygiene rule — *every* `jwt.verify` passes `issuer` and
`audience` — does not. There are currently two such call sites (`logout.controller.ts:76,82`); `jwt.decode` is
used without verification in three more places, two of which are deliberate (`jwt-verification.service.ts:59`
after Authlete has verified, `token-exchange-response.handler.ts` not at all) and one of which was a finding
(the `id_token_hint` path, `RPL-…` F-3).

> **Partly satisfied 2026-08-11 (T0-2).** The `id_token_hint` call site is now a `jwt.verify` that passes both
> `issuer` and `audience`, and pins the algorithm list — i.e. it is the first site written to this rule, and
> `utils/verify-id-token-hint.ts` is the worked example **JOSE-W1** should point the remaining sites at. The two
> `logout.controller.ts:76,82` back-channel sites still pass neither option, so **JOSE-W1 ⊃ BCL-W1 remains open**
> (`04-remediation-plan.md` T1-14). Note the new site also decodes the header first, purely to select a key —
> that is safe, and the distinction (decode to *route*, verify to *trust*) is the one this rule turns on.

## Finding F-3 — the JWK Set is served under `/api` and advertised on a tunnel host (S3, cross-reference)

`jwks_uri = https://cecile-soapsudsy-zoila.ngrok-free.dev/api/.well-known/jwks.json` (probe 3), and the route is
`GET /api/.well-known/jwks.json` (`routes/jwks.routes.ts:6`). So the advertised URI and the served path **do**
agree — this is self-consistent, unlike OIDC Discovery, which is advertised at an issuer that does not serve it.

Two residual issues, both inherited rather than new:

1. **The host is the ephemeral tunnel** (probe 2 §5), so every key consumer's cached `jwks_uri` breaks when it rotates. For a JWK Set that is worse than for other endpoints: a verifier that cannot fetch the set cannot validate any token, and RFC 7517 offers no fallback.
2. **`/api/.well-known/` is a non-standard location for a well-known URI.** RFC 8615 reserves `/.well-known/` at the origin root. This is B3's finding for discovery; the JWKS URI is exempt from any *correspondence* rule because it is advertised explicitly, so it is legal — but it means the repo has three different placements for well-known documents (root for OAuth AS metadata, PRM, VCI and federation; `/api` for discovery and JWKS), which `00-inventory.md` §3.1 records and nothing explains.

## Finding F-4 — the JWKS controller converts a 204 into a 200 with an empty key set (S4)

`controllers/jwks.controller.ts:17-21` special-cases an SDK `statusCode === 204` into `200 {"keys":[]}`.

RFC 7517 §5 requires a JWK Set to have a `keys` member, so a 204 with no body is not a valid JWK Set document, and
returning `{"keys":[]}` is a defensible normalisation — a consumer gets a well-formed empty set rather than a
bodyless success. `01-spec-matrix.md` and `00-inventory.md` §5 both record it as a deliberate special case.

Worth one note: an empty key set and an unreachable key set are very different conditions for a verifier, and both
now present as `200 {"keys":[]}`. Since the service does have keys (ES256 present, per the advertised algorithm
lists), this path should never fire in practice — if it ever does, it means the service lost its keys, and 200 is
the wrong way to say so. Related in spirit to `ERRORHANDLER-STATUS-INVERSION.md`: a failure being reported with a
success status.
